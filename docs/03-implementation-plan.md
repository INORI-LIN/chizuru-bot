## 0. 状态标记与文档约定

沿用需求文档第 1.1 节的状态标记：

- **已确认**：用户明确选择的需求，实施时不能擅自删减。
- **设计基线**：本方案采用的实现或产品规则，不代表框架默认具备。
- **建议参数**：可调整的初始值，部署前评审，不是性能承诺。
- **待核验**：需要对选定软件版本、运行环境或实际账号验证。

任务卡附加标记：

| 标记 | 含义 |
|---|---|
| `【阻塞】` | 前置依赖用户决策（见第 9.2 节）或 S0 核验结论；未满足前不得开工 |
| `【待审】` | 已有草案但需用户审阅定稿（见第 9.1 节与附录 C）；定稿前该任务不得视为完成 |
| `【已完成】` | 该任务的交付物已落地并通过其完成判据的离线部分；在线部分仍按各自标注 |
| `【授权】` | 开工前需要用户就本阶段范围再次明确授权 |
| `【在线】` | 验证必须使用真实 QQ/NapCat/DeepSeek 或受控在线实例，不能只靠离线测试 |

## 1. 目的与使用方式

### 1.1 本文的作用

把需求文档的完整首版目标（R-QQ—R-ENV）与架构文档的信任边界、数据生命周期、并发和故障策略，拆成**带依赖、可独立验证的细粒度任务卡**，让每一步都有明确的开工条件、产出物和完成判据。

### 1.2 三条使用规则

1. **不重定义编号。** 需求编号（R-*）与验收编号（A*）以[需求文档](./01-requirements.md)为准。本文只做映射，不新增、不修改、不弱化任何一条需求或验收标准。若本文与需求文档冲突，以需求文档为准并回改本文。
2. **按阶段推进，按门禁放行。** 阶段门禁未记录，不得宣称该阶段完成。**S0 阶段门于 2026-09-17 由用户决定有意跳过**（不是通过）：离线部分已完成并留证（附录 D），在线部分仍未验证。跳过决定与其代价见第 9.4 节。
3. **参数不是承诺。** 需求文档第 6 节的窗口、TTL、并发、期限是设计初值。实现按这些值落地，但**通过验收不等于达到性能指标**，实施后仍需按真实模型、群规模和预算复核。

### 1.3 任务卡字段

| 字段 | 含义 |
|---|---|
| 任务 | 唯一编号，形如 `S2-03`；编号一旦分配不再复用 |
| 目标 | 一句话说明这项任务要达成什么 |
| 依赖 | 必须已完成的先行任务编号 |
| 交付物 | 可检查的产出（模块、测试、记录、清单） |
| R | 服务的需求编号 |
| A | 对应验收用例编号；空白表示属于基建或门禁，不直接对应验收 |
| 完成判据 | 判定"完成"的可验证条件 |

### 1.4 本文的交付边界

本节原描述**文档阶段**的交付边界（本文 0.1 版时确实只有两份文档）。自 2026-09-17 起本文所述内容已开始落地：`scripts/s0/` 与 `astrbot_plugin_chizuru/` 下标注 `【已完成】` 任务的模块已真实存在，其余仍是**拟议结构**。判断某文件是否存在请直接看仓库，不要以 §3.2 的目录树为现状清单。

### 2.3 已知阻塞（不得绕过）

架构文档 §14.4 第 4 条：`WakingCheckStage` 早于插件执行，且其自身可直接发送错误/权限提示。因此**当前骨架不得加载到混有其他插件的在线实例**，`G02 严格触发` 尚未通过。

本次源码复核进一步确认了这一阻塞的结构性原因（详见第 3.4 节约束 K1—K3）：只要任一插件 handler 的 filter 通过，事件就被标记为 `is_wake` 而不再自动停止；私聊在默认配置下直接唤醒；`ProcessStage` 在 handler 之后还有第二条默认 LLM 路径。

这意味着"严格 @"**不可能只靠插件优先级实现**，必须同时：只启用本插件、关闭内置命令与相关原生能力、并由插件对每个事件显式收口。这是 S0 的核心核验对象。

## 3. 代码模块与文件结构

以下为**拟议结构，本轮不创建任何文件**。

### 3.1 设计原则

1. **增量扩展，不替换。** 在现有 `main.py` / `policy.py` / `config.py` 上扩展，保留既有函数签名与测试语义。**既有测试必须继续通过**，不得为了让新功能通过而放宽既有断言；确实需要改变期望值时（如 S1-03 的媒体分流），必须同时说明原保证如何被保留。
2. **纯逻辑与框架耦合分离。** 新增模块尽量是可直接单元测试的纯逻辑；框架耦合集中在 `main.py`（生命周期与钩子）与 `llm.py`（提供商调用）。
3. **单一出站装配点。** 出站只经 `main.py` 装配的受控路径，且必须过 `send_gate.py`。
4. **单一记忆写入入口。** 任何长期记忆写入都必须经过同一个授权与类型检查入口（架构 §4.5）。

**S1-03 的分工决定（2026-09-17，采用方案 1）**

原判据同时要求"新增 CONTROL_COMMAND / CHAT / BUFFER_ONLY 分流"与"现有 8 项策略测试继续通过"，两者互相冲突：现有 `tests/test_policy.py` 断言的正是"非触发即 `IGNORE`"，而允许群内的普通群聊一旦归入 `BUFFER_ONLY`，这些期望值就必须改写。

**决定：`classify` 只判定触发形态，不承担采集资格与指令分流。**

| 关注点 | 归属 | 理由 |
|---|---|---|
| 触发形态 | `policy.py`（本任务） | 只依赖可信事件元数据与顶层消息组件 |
| 采集资格 | S2 采集规则 | 需求 §4.1 原文即"**符合采集规则时**只进短期缓冲"；告知、群开关、成员退出都是 S2 的状态 |
| 指令 / 聊天分流 | `commands.py`（S1-05） | 判断一句话是不是指令需要指令语法知识；放两份会各自漂移 |

因此 `Classification` 的实际取值为 `IGNORE` / `EMPTY_OR_UNSUPPORTED` / `UNSUPPORTED_ATTACHMENT` / `TEXT_CANDIDATE`，**不含** `BUFFER_ONLY` / `CONTROL_COMMAND` / `CHAT`。`UNSUPPORTED_ATTACHMENT` 是本次新增：需求 §4.1 对"空 @"（忽略）与"@ 后只有图片/语音/文件"（可回固定能力提示）分档，两者必须能区分。

现有 8 项策略测试原样通过；`tests/test_plugin.py` 中"@ 后仅图片"的期望值由 `empty_or_unsupported` 改为 `unsupported_attachment`——这是行为分化而非判据弱化，"不解析附件、不请求模型、不出站"的保证不变，并新增了图片/语音/视频/文件四个用例。

**S1-07/08/09 的实施判断（2026-09-17）**

三项任务都只交付纯逻辑模块；框架接入与钩子注册在 S1-14。以下判断影响完成判据的解释：

| 事项 | 决定 | 理由 |
|---|---|---|
| 去重窗口取值 | **由调用方显式注入，模块内不设默认值** | S1-08 的依赖 S0-08 仍是在线待验证（R10/O-07：message_id 稳定性与重连回放窗口）。本任务交付的是机制与两条上界（容量 + TTL），取值待在线结论；先写一个数字会把未核验假设伪装成参数 |
| 队列上界口径 | 只约束**未被准入的等待者**：运行中的任务另计 | "待处理"即尚未开始处理；否则 `chat_queue_per_group=3` 会被读成"最多 3 条消息在飞" |
| 预算与调度的关系 | **解耦**：`scheduler.py` 不认识预算 | 调度器同时服务聊天与抽取（S3），强绑凭据只增加耦合而不带来真实强制；"先预留、再调度、后结算"的顺序由 S1-14 的单一装配点保证 |
| 上限判定口径 | "已用 + 在途 vs 阈值"，不含新任务自身的估算 | 使 `paused` / `extraction_allowed` 的结论与 `reserve` 始终一致；代价是最后一次放行可能让结算后总量超过上限，超出量不超过一次预留估算，此后立即停用 |
| 抽取停用阈值 | `EXTRACTION_STOP_RATIO = Decimal("0.9")`，属**建议参数待评审** | 需求 §6 与架构 §7.2 要求"临近上限保守暂停，抽取优先停用"但未给系数，且 B2 暂不设金额因而当前不生效；评审若不要提前停用，改为 `Decimal(1)` 即可 |
| 去重 `release()` 逃生口 | 仅允许在**确认未产生任何副作用**时撤销占用（如队列满、预算拒绝） | 否则重连回放会被永久判为"已处理"，用户再也得不到回复；已由测试钉住 |
| 调度器的任务所有权 | 不创建后台任务；在途工作运行在调用方任务里 | `_pump()` 由 `submit()` 与任务完成同步驱动，不用 `asyncio.Semaphore`（其唤醒是 FIFO，无法表达聊天优先）；`terminate` 只需取消调用方任务并 `aclose()`，不会留下调度器持有的悬挂 task |

**已知限制（不因本批落地而改变）**：① 历史窗口 20 轮/24 小时是**插件侧**的取值，框架仍无原生 TTL；② 写回与并发清空（S2-04 退出、将来的 S2-05 关闭）之间是"**收窄而非原子**"的窗口，最终一致性靠发送前/写回前的两次修订比对；③ 昵称转义只承诺"不新起一行、不出现角色冒号、不超长"，昵称形如"成员2"的混淆属残余风险；④ 真实 token 数与真实会话行为仍待在线校准（S4-02）。

| 测试基建（**新增注入点 1 个**） | `plugin.price_table`（测试注入点，生产 `None` → 空价目表） | 不注入价格时抽取**跑不到写回**：金额未配置会被 `extraction_allowed` 挡住，配了金额又被 `PRICE_UNKNOWN` 挡住。这是 B2 + R20 两个已确认决定的合成结果，不是缺陷；注入点让"已授权且预算齐备"的链路可离线留证 |
