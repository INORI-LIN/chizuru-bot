## 0. 状态标记与文档约定

沿用需求文档第 1.1 节的状态标记：

- **已确认**：用户明确选择的需求，实施时不能擅自删减。
- **设计基线**：本方案采用的实现或产品规则，不代表框架默认具备。
- **建议参数**：可调整的初始值，部署前评审，不是性能承诺。
- **待核验**：需要对选定软件版本、运行环境或实际账号验证。

任务卡附加标记：

| 标记 | 含义 |
|---|---|
| `【阻塞】` | 前置依赖用户决策（见第 9.2 节）或 S0 核验结论；未满足前不得开工 |
| `【待审】` | 已有草案但需用户审阅定稿（见第 9.1 节与附录 C）；定稿前该任务不得视为完成 |
| `【授权】` | 开工前需要用户就本阶段范围再次明确授权 |
| `【在线】` | 验证必须使用真实 QQ/NapCat/DeepSeek 或受控在线实例，不能只靠离线测试 |

## 1. 目的与使用方式

### 1.1 本文的作用

把需求文档的完整首版目标（R-QQ—R-ENV）与架构文档的信任边界、数据生命周期、并发和故障策略，拆成**带依赖、可独立验证的细粒度任务卡**，让每一步都有明确的开工条件、产出物和完成判据。

### 1.2 三条使用规则

1. **不重定义编号。** 需求编号（R-*）与验收编号（A*）以[需求文档](./01-requirements.md)为准。本文只做映射，不新增、不修改、不弱化任何一条需求或验收标准。若本文与需求文档冲突，以需求文档为准并回改本文。
2. **按阶段推进，按门禁放行。** S0 是硬门控阶段。S0 未通过前，S1 及其后阶段不得开工；阶段门禁未记录，不得宣称该阶段完成。
3. **参数不是承诺。** 需求文档第 6 节的窗口、TTL、并发、期限是设计初值。实现按这些值落地，但**通过验收不等于达到性能指标**，实施后仍需按真实模型、群规模和预算复核。

### 1.3 任务卡字段

| 字段 | 含义 |
|---|---|
| 任务 | 唯一编号，形如 `S2-03`；编号一旦分配不再复用 |
| 目标 | 一句话说明这项任务要达成什么 |
| 依赖 | 必须已完成的先行任务编号 |
| 交付物 | 可检查的产出（模块、测试、记录、清单） |
| R | 服务的需求编号 |
| A | 对应验收用例编号；空白表示属于基建或门禁，不直接对应验收 |
| 完成判据 | 判定"完成"的可验证条件 |

### 1.4 本文的交付边界

本轮**只交付本文档**。文档中出现的目录树、模块名、配置项全部是**拟议结构，尚未创建**：`astrbot_plugin_chizuru/` 下除现有 `__init__.py`、`main.py`、`config.py`、`policy.py`、`metadata.yaml`、`_conf_schema.json` 之外没有别的文件，仓库顶层也不存在 `scripts/`。

### 2.3 已知阻塞（不得绕过）

架构文档 §14.4 第 4 条：`WakingCheckStage` 早于插件执行，且其自身可直接发送错误/权限提示。因此**当前骨架不得加载到混有其他插件的在线实例**，`G02 严格触发` 尚未通过。

本次源码复核进一步确认了这一阻塞的结构性原因（详见第 3.4 节约束 K1—K3）：只要任一插件 handler 的 filter 通过，事件就被标记为 `is_wake` 而不再自动停止；私聊在默认配置下直接唤醒；`ProcessStage` 在 handler 之后还有第二条默认 LLM 路径。

这意味着"严格 @"**不可能只靠插件优先级实现**，必须同时：只启用本插件、关闭内置命令与相关原生能力、并由插件对每个事件显式收口。这是 S0 的核心核验对象。

### 2.4 骨架与目标的能力落差

| 维度 | 骨架 | 首版目标 | 差距性质 |

| 触发 | 分类后静默停止 | 严格 @ 门控 + 分流（缓冲/命令/聊天/空@） | 框架级验证 + 实现 |
| 出站 | 零出站 | 唯一受控出站路径 | 新增，且需覆盖审计 |
| 上下文 | 无 | 内存环形缓冲 + 受控临时注入 | 新增 |
| 存储 | 无（测试禁止建库） | 插件专用 SQLite + 修订号 | 新增，且需改造测试守卫 |
| 记忆 | 无 | 授权 → 抽取 → 隔离检索 → 修订失效 | 新增 |
| 运维 | 无 | 有界队列、并发、预算、脱敏日志、降级 | 新增 |
| 验证 | 16 项离线测试 | A01—A19 全矩阵 | 大部分需真实环境 |

## 3. 代码模块与文件结构

以下为**拟议结构，本轮不创建任何文件**。

### 3.1 设计原则

1. **增量扩展，不替换。** 在现有 `main.py` / `policy.py` / `config.py` 上扩展，保留既有函数签名与测试语义。现有 16 项测试必须继续通过，不得为了让新功能通过而放宽既有断言。
2. **纯逻辑与框架耦合分离。** 新增模块尽量是可直接单元测试的纯逻辑；框架耦合集中在 `main.py`（生命周期与钩子）与 `llm.py`（提供商调用）。
3. **单一出站装配点。** 出站只经 `main.py` 装配的受控路径，且必须过 `send_gate.py`。
4. **单一记忆写入入口。** 任何长期记忆写入都必须经过同一个授权与类型检查入口（架构 §4.5）。

### 3.2 拟议目录树

```text

  main.py              【扩展】Star 生命周期 + 全部钩子注册 + 服务装配（唯一框架入口）
  config.py            【扩展】Settings 分组化，保持 fail-closed
  policy.py            【扩展】纯触发分类
  keys.py              【新增】隔离键与修订号快照
  commands.py          【新增】控制指令纯解析
  control.py           【新增】确定性权限判定与状态变更
  context_buffer.py    【新增】群普通消息内存环形缓冲
  context_assembly.py  【新增】临时材料装配
  llm.py               【新增】提供商调用封装、错误分类、有限重试
  budget.py            【新增】用量与预算核算
  scheduler.py         【新增】有界队列、并发信号量、业务期限
  send_gate.py         【新增】发送前复核与结果丢弃

```

|---|---|---|---|

### 3.5 需显式声明的设计判断

以下两条是**新增的设计选择**，两份既有文档未指定，因此必须在本文声明并由 S0 实测确认：

1. **普通群消息采集的钩子形态。** 拟采用宽 filter 的 `on_message` 进行采集（复用 K13 的机制形态），并接受它会因 K1 使事件被视为 wake；随后用 `should_call_llm(False)` + `stop_event()` 收口。若 S0-03 证明该副作用无法被覆盖，改用其他已审计方案或回设计评审。
2. **非 @ 与私聊的兜底责任在插件。** K2、K3 表明框架默认行为并不满足"仅被 @ 时回复"，因此由插件对每个事件显式收口；框架侧配置（`disable_builtin_commands`、`no_permission_reply`、`friend_message_needs_wake_prefix` 等）在 S0-02 列为必核清单。

### C.1 群告知文案

**用途**：群维护者在开启普通群聊采集前发布给群成员。需求 §4.2 要求完成告知、允许名单与成员退出入口配置后才可开启采集，且**告知之前不补采历史消息**。

**交付机制（2026-09-17 确认；命令见需求 §4.4，展开说明见第 9.1 节 B1a）**

| 步骤 | 动作 | 系统行为 |
|---|---|---|
| 1 | 本群授权维护者通过真实 @ 发送「群上下文 开启」 | **只回复本文案全文与操作指引**；不开启采集、不写告知版本；记录待确认状态（群键 + 发起维护者 + 发起时间 + 文案版本） |
| 2 | 维护者把机器人这条回复设为群公告，或转发并置顶，完成对群成员的告知 | 无 |
| 3 | 同一维护者在 5 分钟内、同一群内 @ 机器人发送「群上下文 确认开启」 | 写入告知版本、告知时间、告知人（架构 §6.1 群策略表已有告知版本字段，无需新增表），随后开启采集 |

**明确不做**：机器人不主动发送告知；不在未 @ 时推送；不补采告知完成前的历史消息。

**文案版本**：建议从 `notice-1` 起编号。文案一旦修改必须递增版本并重新告知——否则已告知成员看到的内容与实际采集行为不一致。此版本号同时是 S2-02 完成判据中的"告知版本可追溯"的取值来源。

```text
  复你时让对话更连贯。提取在后台完成，我不会在群里主动说"我记住了"。

· 会保存什么
  你的称呼偏好、回复长短偏好、一般兴趣、非敏感的活动偏好。
  不保存密码、口令、电话、住址、证件、财务或健康信息，也不保存别人
  的隐私、关系推断，或你没说过的标签。

· 保存在哪里、存多久
  保存在本机数据库，最多 20 条，90 天后失效，到期即停止使用并清除。
  提取和回复时，必要内容会发送给 DeepSeek 处理。

· 谁能看到
  只有你本人可以查看、纠正或删除自己的记录，别人问起我不会说。
  但请注意：你在本群查看记录时，内容会发在群里，其他成员可能看到。

· 怎么撤回
  随时 @ 我发送「记忆 关闭」或「记忆 删除全部」，即可撤回授权并清除
  已保存的记录。撤回后需要重新确认才能再次开启。

· 只对开启后的内容生效
  确认开启后，我只处理此后产生的内容，不会追溯开启之前的聊天。

确认开启请回复「记忆 确认开启」，5 分钟内有效。
```

### C.3 群内查看记忆提示

**用途**：需求 §4.3 要求查看列表只在本人明确 @ 发起时返回，并提示这是群内可见操作；首版不增加私聊查看通道。

```text
【提示】接下来我会把你在本群的记忆记录列在这里。
这是群内消息，其他群成员可以看到。

继续请回复「记忆 查看 确认」。
```

**需在审阅时确认的设计选择**：上面采用两步确认——首次「记忆 查看」只返回提示、不返回列表，第二次「记忆 查看 确认」才列出内容（沿用需求 §6 的 5 分钟确认有效期）。需求文档只要求"提示"，未规定必须分两步。

- 若采用两步：提示才有实际意义，代价是多一次交互。
- 若合并为一步：提示与列表同时发出，则提示已无保护作用，等于只做告知。

**建议采用两步**，与「记忆 开启 / 记忆 确认开启」的既有形态保持一致。

### C.4 剧透保守策略

**用途**：S1-11 固定系统规则的一部分，也是 S4-05 人设人工评审的判据之一。对应需求 §3.1"对不确定的剧情细节不编造原作事实；未确定剧透范围时尽量不主动透露关键剧情"。

```text
【剧透与剧情准确性规则】

· 不主动透露《租借女友》的关键剧情、结局、角色关系转折与重要设定。
· 被直接询问剧情时，可以说明这是一部有原作的作品，但不展开关键情节，
  可以建议对方自行观看。
· 对不确定的剧情细节一律承认不清楚，不编造原作事实、角色经历或设定。
· 不把群成员默认当作原作人物，不默认存在恋人、亲属等关系。
· 不对作品的未公开内容或后续发展作预测性断言。
· 若群维护者另行指定可讨论范围，以该范围为准。
```
