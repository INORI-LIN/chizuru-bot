## 1. 架构目标与约束

采用 **AstrBot 单实例 + NapCat + 一个职责受限的项目插件 + 本地 SQLite**。复用框架的平台适配、模型提供商、人格、会话和管理能力，仅扩展严格触发、受控群上下文和授权成员记忆。

初始文档阶段已经完成，用户随后授权了最小插件骨架与 uv 环境实施。第 1—13 节描述完整目标设计，不表示这些能力已经实现；当前实际产物和离线验证范围以第 14 节为准。未启动 WebUI、NapCat、QQ 连接或 DeepSeek 调用。

### 1.1 关键决策

| 决策 | 原因 | 取舍与需求映射 |
|---|---|---|
| 普通 QQ 账号通过 NapCat 接入 | 用户已选择 | 承担非官方接入兼容性与账号风险；R-QQ |
| 单 AstrBot 实例，不拆微服务 | 小规模群机器人优先简单、可诊断 | 暂不做水平扩展；R-OPS |
| 原生提供商调用 DeepSeek | 不重复开发模型网关、客户端与配置面板 | 需要验证所选版本兼容实际模型；R-CHAT |
| 一个项目插件 | 把触发、授权及数据边界放在可审查范围 | 仍须证明其钩子能覆盖必要路径；R-TRG、R-CTX、R-MEM |
| 普通群消息受控缓冲，不直接打开原生群聊注入 | 需要 TTL、成员退出、动态上下文不进入 system 或永久历史 | 复用事件和提供商，但增加小范围采集逻辑；R-DATA |
| SQLite + 有界内存 | 数据量小，无需额外数据库服务 | 只支持单实例，重启丢弃临时任务；R-MEM、R-OPS |
| 人格固定、群聊/记忆动态分层 | 不可信内容不获得系统指令地位 | 模型仍可能受提示注入影响，权限必须程序化；R-PER、R-DATA |
| AstrBot 源码项目使用 uv | 统一 Python、依赖和运行流程 | 必须单独处理插件依赖与外部 NapCat 版本；R-ENV |

本文的参数以需求文档第 6 节为唯一基线；官方能力、设计要求和待核验项明确分开。

## 2. 组件与信任边界

```text
QQ 群成员
   ↕ QQ 消息
NapCat / QQ 登录态                      独立进程或受控容器
   ↕ OneBot v11 反向 WebSocket
   │ NapCat 为客户端，AstrBot 为服务端
┌──────────────────────────────────────────────────┐
│ AstrBot 单实例（Python / uv）                      │
│  OneBot 适配器 → 消息事件 → 入站策略与命令分流      │
│                           │                       │
│  项目插件                 ├─ 普通群聊有限缓冲      │
│  · 严格 @ / 允许群        ├─ 授权与退出控制        │
│  · 动态上下文拼装         ├─ 低敏记忆检索/抽取     │
│  · 数据修订与清理         └─ 发送前校验            │
│                           ↕                       │
│                   插件专用 SQLite                 │
│                                                   │
│  原生人格 / 会话管理 → 原生模型提供商              │
│  原生回复发送 ← 回复处理与策略校验                 │
│  原生 WebUI / 受限日志                            │
└──────────────────────────────┬───────────────────┘
                               ↕ HTTPS
                         DeepSeek API
```

图中逻辑节点不表示独立服务或新增公开 HTTP 接口。

### 2.1 各组件职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| NapCat | QQ 账号连接、协议事件、消息发送 | 人格、长期记忆、Python 依赖管理 |
| AstrBot 适配器 | 接受 OneBot 事件，映射发送者/群/消息链，发回 QQ | 决定成员是否同意长期记忆 |
| 原生人格与会话 | 固定角色设定、互动历史、原生模型调用流程 | 自动满足成员授权/退出/TTL 等项目策略 |
| 项目插件 | 严格触发、受控群缓冲、确定性控制命令、记忆生命周期与请求/发送校验 | 新建通用 Agent 框架或替代整个 AstrBot |
| 原生模型提供商 | 鉴权、调用 DeepSeek、解析返回 | 让云端代替本地会话管理 |
| 插件 SQLite | 状态、低敏事实、修订和必要去重元数据 | 保存全量群聊或模型推理过程 |
| WebUI/日志 | 管理和运维诊断 | 面向群成员公开服务或公开成员档案 |

### 2.2 信任边界

1. QQ 消息、昵称、引用、模型响应及提取出的候选记忆均是不可信内容。
2. 发送者身份、群 ID、机器人 ID 来自已鉴权的平台事件；昵称仅用于展示。
3. DeepSeek 是外部数据处理方，只发送本轮必要内容，不发送 QQ 登录态、密钥或完整成员表。
4. 即使内容被放在用户角色或结构化边界中，也不能保证模型绝不受提示注入影响；关键权限、数据检索范围、授权变更与发送门控由程序执行。
5. 首版不开启模型工具、联网、代码执行或外部 MCP 接口，减少与聊天无关的权限面。

## 3. 复用 AstrBot 的边界

资料核实日期：2026-09-16。下表来自官方文档，不代表对某个已安装版本的源码审计。

| 领域 | 已核实文档能力 | 本项目策略 / 尚需验证 |
|---|---|---|
| OneBot v11 | 支持反向 WebSocket，AstrBot 为服务端 | 开启 Token、限制监听接口；验证断连与回放行为 |
| 人格 | WebUI 人格管理，配置可选择默认人格 | 不写已废弃的内联 persona 数组；限制普通成员切换人格 |
| 群会话 | `platform_settings.unique_session` 控制支持渠道的成员隔离 | 采用群共享对话；再按机器人实例校验隔离，不仅依赖群号 |
| 发言人信息 | 事件包含 self_id、group_id、message_id、sender、message、timestamp；`identifier` 可附加名字 | 使用可信 ID 映射短标签，避免昵称伪装系统/其他成员。**已落地（S2-06）**：单请求内 `成员1…` 标签 + 转义限长昵称，见 §5.1 |
| 群聊感知 | `provider_ltm_settings.group_icl_enable` 暂存群消息并注入 system | 本设计关闭，使用受控缓冲与动态用户内容，避免重复注入和额外永久保存。**已落地（S2-03/S2-06）**：内存缓冲 + `extra_user_content_parts`（user 侧） |
| 历史限制 | 有轮数限制、截断及 LLM 压缩 | 首版用截断；TTL、删除和不落历史策略须验证接口，不假定全部原生满足。**已落地（S2-07）**：框架无原生 TTL，插件在读写两侧执行 20 轮/24 小时，时间戳走条目私有键 `_at`，见 §6.1 |
| 请求钩子 | `on_llm_request` 可修改 ProviderRequest；动态数据可进 `extra_user_content_parts` | 临时动态材料使用可验证的不持久化路径。**本项目不走 `on_llm_request`**：直调 `Provider.text_chat` 时经 `extra_user_content_parts` 传入（S2-06），历史经 `contexts`（S2-07） |
| 临时标记 | `mark_as_temp()` 文档注明 AstrBot >= v4.24.0 | 选定版本须包含该能力或等价的受验证方案，不能默默保存材料。**已落地（S2-06）**：part 级 `mark_as_temp()`；本插件不经过 `_save_to_history`，整轮排除由"历史写回只接收纯文本问答"承担（§6.2） |
| 回复钩子 | 有 `on_llm_response`、`on_decorating_result`、`after_message_sent` | 钩子不天然覆盖任意直接发送；只启用审计过的发送路径 |
| 事件传播 | 监听器可按类型过滤，支持优先级及终止传播 | 先证明非唤醒事件可采集且严格门控先于命令/模型；不猜执行顺序 |
| 允许名单 | 有白名单；文档说明空名单不进行过滤 | 项目允许群列表必须非空；缺失或空列表按“全部关闭”解释 |
| 模型 | 支持 OpenAI Compatible，保存/获取模型、测试模型 | 首选验证通过的 DeepSeek 提供商；兼容模式不代表支持所有参数 |
| 部署 | 源码部署支持 uv，当前文档要求 Python >=3.12 | 固定具体版本与锁；插件依赖安装后端仍需核验 |

### 3.1 需关闭或审计的冲突功能

- 非 @ 唤醒前缀、空 @ 等待续聊与其自动 LLM 回应。
- 主动回复、定时推送、欢迎、私聊聊天、自动图片描述。
- 未经审核的插件自动回复或直接发送、模型工具调用、推理内容展示。
- 自动 WebUI 升级、运行时依赖自动修复/安装中可能绕回 pip 的路径。
- 原生群聊自动注入与其他收集聊天、长记忆、摘要插件，避免双份存储和隐私策略冲突。

优先配置现有能力；配置不能保证的部分由项目插件处理。若所选版本钩子不能在必要阶段拦截或清理，作为 S0 阻塞回到设计评审，不以临时堆叠插件或静默修改框架核心绕过。

## 4. 消息处理流程

### 4.1 入站分类

1. 适配器验证连接并提供结构化事件。确认机器人实例、群、发送者和消息 ID。
2. 只处理显式允许群；私聊、机器人自身消息、含 @全体的消息和未允许群直接忽略，不进入缓冲。
3. 基于消息链判断是否存在指向当前 self_id 的真实 At 段。引用中的历史 At 不算本次触发。
4. 对重复事件查重；同一事件不能重复回复或重复产生记忆任务。
5. 分流为普通群聊缓冲、有效 @ 控制命令、有效 @ 聊天，或空 @ / 不支持输入。

必须验证与 AstrBot 默认命令处理顺序的关系：不能先让内置命令产生回复，再用后置插件“决定不响应”。

### 4.2 普通群消息路径（R-CTX）

- 检查群已告知并开启、成员未退出、服务未暂停，必要状态可读取。
- 只接受有限长度的直接文本，排除机器人自身输出、命令、媒体、合并转发与可识别引用，尽量过滤明显敏感内容。
- 保存到当前群的内存环形缓冲，执行条数和 TTL 淘汰。
- 不请求 DeepSeek、不抽取长期记忆、不发送任何群消息。
- 保留原消息 ID 和成员归属用于排除、去重和失效，不把成员全集发送给模型。

### 4.3 有效 @ 聊天路径（R-TRG、R-CHAT）

1. 检查群聊天开关、输入类型、限流、队列及模型预算。保留源事件关联标识。
2. 获取当前群会话串行处理权，受全局并发和总业务期限约束；复用或协调原生会话锁，不重复获取造成死锁。
3. 读取当前群数据修订号、当前成员授权修订号；筛选有效历史与未退出成员的普通缓冲。**已落地（S2-06/S2-07）**：装配前取一次修订号快照，发送前重读并比对（§6.2）。
4. 若当前成员已授权且记忆读取可用，检索其在本群的少量相关低敏记忆。任何查询都包含完整隔离键，不由模型传入任意成员 ID。
5. 拼装固定人格、合格互动历史、本轮用户输入、临时群上下文和临时记忆；去重相同消息，限制总 token。**已落地（S2-06/S2-07；记忆层待 S3）**：材料经 `extra_user_content_parts`（临时标记）、历史经 `contexts`，两者由同一 8192 预算裁剪；超预算且无法裁剪时不调用、不发送。
6. 通过 AstrBot 原生提供商调用 DeepSeek。不追加工具权限、不把元数据交给模型当授权依据。
7. 处理模型结果：仅使用正式回复内容；空结果、超时或错误走有限降级。生成结果不能直接更改记忆或执行控制命令。
8. 发送前复核源事件、群开关、授权/数据修订号、允许范围。隐私状态发生变化则丢弃结果，必要时在有效 @ 范围内返回固定的重试提示。**已落地（S2-06/S2-07）**：修订号不一致一律丢弃且不写历史；固定提示文案仍属待评审。
9. 经原生适配器发回源群并记录发送状态；若使用了长期记忆，这一整轮不加入共享互动历史。其他轮次也不得永久保存临时上下文。**已落地（S2-07）**：只有送达成功才写回"纯文本问答"一对；控制命令与记忆辅助轮不经该入口（后者待 S3-08）。
10. 满足授权、预算和队列条件时，将本轮成员原话送入受控自动提取任务。它不阻塞发送，不产生额外群通知。

机器人输出不进入普通群聊缓冲。避免“长期记忆 → 回答 → 群缓冲/共享历史 → 另一成员”的间接跨成员传播；已发送的 QQ 群消息本身可见，不能承诺删除或隐藏。

### 4.4 控制命令路径（R-CTRL、R-ADM）

- 严格 @ 后先识别项目控制命令，核验真实事件身份，再执行确定性状态变更；不送入 LLM 聊天。
- 记忆开启分“展示说明”和“本人确认”两步，授权确认在同群、同成员且有效期内生效。
- 群上下文开启分“展示告知”和“维护者确认”两步，告知版本在同群、同维护者且有效期内记录后才启用采集；告知全文由维护者转发，机器人不主动发送。**已落地（S2-02）**：`群上下文 开启` 逐字回复告知全文并记录 5 分钟待确认窗口，`群上下文 确认开启` 在窗口内同群同人时写入版本/时间/告知人；窗口不满足时重发全文并重开窗口。告知文案与部署配置的版本不一致时一律拒绝（R22）。
- 状态、删除和暂停操作不排在长时间模型生成之后；更新修订号可使在途工作失效。**已落地（S2-05）**：`群上下文 关闭`、`上下文 清空`、`千鹤 暂停/恢复` 都是同步状态变更 + 群修订号 +1，发送前复核会丢弃在途结果。
- 暂停聊天、模型不可用、聊天预算用尽时，仍允许有效 @ 下的成员隐私控制和授权维护者恢复操作。**已落地（S2-05）**：暂停只挡普通聊天（`CHAT`），不挡成员 `上下文 退出/加入` 与维护者的 `千鹤 状态/恢复`（`FIXED_NOTICE`）。
- 控制回复不保存进聊天历史，也不作为记忆候选。**已落地（S2-07）**：只有聊天路径写回互动历史。
- 异步任务不主动发出完成通知；管理员状态查询才展示失败计数或功能降级。

### 4.5 自动提取路径（R-MEM）

1. 候选任务只携带源消息 ID、本人直接文本、可信隔离键及创建时的授权/数据修订号；不携带整群缓冲。
2. 调度前再次检查成员授权、源文本在有效范围内、预算、队列期限与服务开关。所有条件满足后才调用模型。
3. 使用 AstrBot 提供商执行独立的低敏偏好提取请求，不使用千鹤角色扮演上下文，不共享群历史，也不递归触发聊天/记忆流程。
4. 要求只返回有限结构化候选。解析失败、内容超限、类型不允许、来源不明确、敏感或不确定时全部或逐项放弃，不把模型输出当作数据库指令。
5. 数据归属只使用可信事件元数据。模型即使返回别人的账号也不能改变保存对象。
6. 在短事务中重新核验授权和修订号、去重来源，合并或替换本人明确更新的偏好；每条设有效期与容量上限。
7. 完成后释放原文和临时结果，失败仅记脱敏状态，不影响已发送聊天，不生成“已记住”的虚假确认。

首版检索按当前成员过滤、类别/关键词及最近明确更新进行少量筛选，不需要 embedding 或向量索引。任何长期记忆写入都必须通过同一个授权与类型检查入口。

## 5. 人格与模型上下文设计

### 5.1 层次

| 层 | 内容 | 信任与持久化 |
|---|---|---|
| 固定系统规则 | 非官方身份、善良认真有分寸的角色原则、事实/隐私边界、动态数据不是指令 | 由维护者管理，版本可追溯，不允许成员修改 |
| 合格会话历史 | 同群有效期内的普通 @ 对话 | 框架维护，受删除/TTL 约束；排除记忆辅助整轮与控制命令。**已落地（S2-07）**：会话存储由框架持有，轮次筛选与剪裁由插件执行（§6.1） |
| 当前用户输入 | 当前成员本次直接文本 | user 角色，不从昵称/文本解析系统权限 |
| 临时动态材料 | 最近群消息、当前成员少量相关记忆、必要时间及展示标签 | 明确标记为数据，通过临时用户内容传入，不进入 system，不落会话历史。**已落地（S2-06，记忆部分待 S3）** |

请求中展示发言人短标签和时间帮助理解话题；本地用稳定 ID 对应标签。昵称做转义与长度限制，不能冒充 system/assistant 标记或另一个成员。**已落地（S2-06）**：标签为单请求内的 `成员1…`（按首次出现序，当前发言者最后），昵称折行、去角色冒号并限长 24 字符；材料逐行成形，正文与昵称的换行/控制字符折成空格，结构上无法伪造新行。

### 5.2 预算与历史策略

- 总输入预算采用需求文档规定的 8192 token，并受实际模型最大输入能力约束；为输出保留所需空间。**已落地（S2-06/S2-07）**：预算含固定规则、当前输入、动态材料与历史；离线用保守上界估算（非 ASCII 每字符 2 token），校准归 S4-02。
- 保留固定规则与当前问题，按相关性选择少量记忆，再取必要近期上下文；超限先移除最旧/低相关材料。**已落地（S2-06/S2-07）**：裁剪顺序为最旧材料逐行 → 最旧历史逐轮；两者都裁完仍超（即固定规则 + 当前输入自身超预算）时**拒绝请求**：不调模型、不发送、静默。
- 相同事件不得同时作为当前输入、缓冲和历史重复出现；优先原生互动历史中的一次表示。**已落地（S2-06）**：材料渲染按消息 ID 排除当前事件。
- 当前问题本身过长时提示缩短，不为继续请求而删除关键固定规则。
- 首版使用轮数/时间截断，不启用后台 LLM 群摘要，避免额外成本和难删除的衍生副本。
- 必须显式核对实际模型上下文容量；AstrBot 文档说明自动识别失败且容量为 0 时可能不启用压缩，不能依赖默认推断保护预算。
- 使用临时内容标记不意味着整个响应不会进入历史。记忆辅助整轮排除和删除竞态必须独立验证。

## 6. 状态、存储与生命周期

以下是逻辑实体，不是已创建表或最终 SQL 模型。

### 6.1 隔离与实体

机器人实例键应包含平台连接实例标识及机器人 self_id，避免不同连接复用群号导致串用。

| 实体 | 逻辑键与主要属性 | 生命周期 |
|---|---|---|
| 群策略 | 机器人实例 + 群；聊天/采集开关、告知版本、数据修订号 | 本地持久化；无有效策略默认关闭 |
| 成员状态 | 机器人实例 + 群 + 成员；上下文退出、记忆授权、授权版本、成员数据修订号 | 持久化；与聊天正文分离 |
| 低敏事实 | 上述成员键 + 记录 ID；类别、内容、来源消息 ID、创建/更新/到期时间 | 上限 20 条、90 天；人工纠正优先 |
| 群缓冲项 | 群键 + 消息 ID；发送者、时间、有限文本 | 内存，30 条/10 分钟；退出/暂停即清理 |
| 互动历史 | 群会话对应关系、原生会话引用与清理修订信息 | 由 AstrBot 保存，20 轮/24 小时；本插件只维护必要映射，不复制全历史。**已落地（S2-07）**：框架的会话 `content` 无每条消息的时间戳，因此每条条目附一个私有键 `_at`（epoch 秒）；读取时只承认成对且带 `_at` 的条目，送入模型前剥离（§6.2）。框架若改变该结构，解析会保守丢弃历史，表现为"多轮对话失效"而不是错误数据 |
| 在途任务 | 群键、成员键、源消息 ID、状态修订快照、截止时间 | 有界内存；失效/完成/重启释放 |
| 去重元数据 | 机器人实例 + 群 + 消息 ID + 动作类别；处理中/已处理/发送不确定等 | 有界保留，仅标识与状态，不含原文；实施前核验平台消息 ID 稳定性 |

去重保留窗口应至少覆盖允许处理的事件时效及协议端预期回放窗口；具体值根据联调确定，不以无限保存替代上界。超出消息时效的回放丢弃，不重新聊天或提取。

### 6.2 状态一致性

- SQLite 写入使用短事务；模型请求在事务外完成，不持有数据库事务等待网络。
- 更新授权、退出、纠正或删除时先增加相关修订号，使已有请求/任务失效。
- 普通退出/群清空等可能影响整个群上下文时增加群修订号；成员记忆修改增加成员修订号，并清理必要的共享历史。
- 发起请求、发送与写入均比对快照。修订不一致时放弃旧结果，不自动重做以消耗额外费用。**已落地（S2-06/S2-07）**：受理时快照（群修订 + 当前发言者成员修订），`_deliver` 发送前重读，历史写回前再比对一次；无存储时两侧均为空（不比对，聊天照常）。写回与并发清空之间是"收窄而非原子"的窗口
- 队列取消是优化，修订校验才是阻止旧任务重新写回的最终规则。
- 若原生模型流程在发送校验前已写历史，需要在同一受控会话流程中抑制或清理；无法证明一致性则不能启用相应记忆功能。

### 6.3 删除操作覆盖

| 操作 | 必须处理 |
|---|---|
| 退出普通群上下文 | 持久化退出；清理本人缓冲；清空受影响群历史；失效相关在途结果；不自动撤销独立记忆授权。**已落地（S2-04，群修订 +1）** |
| 关闭群上下文 | 停止普通采集，清缓冲及受影响历史，失效使用该材料的请求。**已落地（S2-05）**：`群上下文 关闭` 写 `context_enabled=0`（群修订 +1）→ 清整群缓冲 → 清受影响会话；聊天不受影响（`关闭` 只停采集） |
| 纠正/删除记忆条目 | 核验本人，变更事实与修订号，取消旧提取候选，清理注入缓存和必要历史。**属 S3** |
| 关闭/删除全部记忆 | 撤回授权，删除事实，禁止读写，取消待提取，失效使用旧事实的请求。**属 S3** |
| 清空群短期上下文 | 清缓冲/互动历史并增加群修订号，不等同删除成员长期记忆。**已落地（S2-05）**：`上下文 清空` = `bump_revision` → 清缓冲 → 清受影响会话；不改采集开关；无存储时仍清内存与会话（只跳过修订号） |
| 正常重启 | 丢弃缓冲和临时任务，保留有效授权/退出状态，对过期事实和历史执行清理。**已落地（S2-07/S2-08）**：缓冲与待确认窗口是纯内存（重启即丢）；退出/暂停/告知状态在 SQLite；互动历史的 20 轮/24 小时在读写两侧执行，并在启动时做一次**裁剪扫描**（只删带 `_at` 的成对条目，框架条目原样保留）；**过期事实**的清理属 S3 |
| 重装/状态不完整 | 群采集和记忆关闭；重新告知/授权，不从旧配置推断成员仍同意。**已落地**（无策略行即关闭；库损坏降级为"无存储"） |

本地删除定义为应用后续不可读取、使用或恢复，不承诺 SSD/文件系统已进行物理安全擦除。操作系统快照、云盘同步、QQ 已发消息及 DeepSeek 已接收数据属于额外边界，应在真实部署说明中告知。

## 7. DeepSeek 接入与成本

### 7.1 配置策略

| 项目 | 设计 |
|---|---|
| 调用入口 | AstrBot 原生 DeepSeek 提供商（如所选版本可用且验证通过）或 OpenAI Compatible；不新建独立客户端服务 |
| Base URL | 官方 OpenAI 兼容地址 `https://api.deepseek.com`，不把完整 chat/completions 路径填为 base |
| 模型 ID | 配置项，部署时获取并测试目标模型，不自动选择列表第一项 |
| 当前文档快照 | 2026-09-16 官方页面推荐 `deepseek-flash`，同时列出 `deepseek-v4-pro`；这不是永久名称或账户可用性保证 |
| 鉴权 | 运行时受限配置，密钥不进文档、仓库或日志 |
| 会话 | API 无状态，AstrBot 每轮提交必要历史；服务端缓存不能代替应用会话 |
| 思考/工具 | 首版不开放工具，尽量采用已验证的低延迟文本模式；不向 QQ 发送 reasoning_content |
| 模型切换 | 受控操作，重新评审输入容量、参数、角色表现与计费；不自动切换第三方提供商 |

是否能关闭思考、是否支持特定参数或响应格式，以实际模型和 AstrBot 提供商兼容性测试为准，不能把 OpenAI 兼容理解为所有功能完全相同。

### 7.2 统一调用预算

- 聊天与记忆提取均经 AstrBot 提供商，使用共享并发限制及独立可见的用量类别。
- 每条有效 @ 最多产生一次聊天任务及一个可放弃的提取任务；重试次数受统一上限约束。
- 抽取只处理本人的短文本且无多轮历史，不发送完整群上下文，以降低成本和数据范围。
- 调度前按最大 token 及已配置价格估算预留成本，返回后按 usage 结算；缺失 usage 要标记估算，不能计为零。
- 日/月预算以用户确认金额及当前服务价格配置；价格变化或统计延迟可能造成估算偏差，不声称本地计费完全等于账单。临近上限保守暂停，另核实提供商侧可用的额度控制。
- 不硬编码价目或永久限流额度；未配置抽取预算时自动记忆提取保持关闭并在状态中明确显示。

## 8. 并发、去重与故障处理

### 8.1 并发与调度

- 全局模型并发 2，同群模型工作并发 1；聊天优先于自动提取。
- 同群聊天顺序由唯一会话串行机制维持，协调 AstrBot 已有锁，避免双锁死锁。
- 群聊天排队 3、全局抽取排队 20，待调度最长 30 秒；后台提取过期就放弃，不持久化无限积压。
- 单任务从接受起最多 45 秒，排队、网络和重试共享剩余时间；连接 5 秒、读取 30 秒仅为该总期限内的上限。
- 暂停/删除等控制操作不能等当前长模型调用释放后才更新授权；状态变更让旧请求失效。
- 模型调用、重连和服务监督器各自职责清晰，不多层无限重试。

### 8.2 幂等与发送不确定性

- 事件接收去重防止重连回放产生重复聊天；记忆写入按源消息和动作查重，不能同一条反复提取写入。
- 记录已经确认发送的结果状态，重复事件不再次发送。
- 请求超时可能已经消耗提供商费用；QQ 发送超时也可能实际上已送达。对发送不确定状态不盲目重发，不虚称 exactly-once。
- `after_message_sent` 钩子不等于用户已读回执；需要核实适配器确认语义。
- 服务重启丢弃未完成内存任务，不自动重播存留正文。必要去重状态按有界窗口持久化，避免常见重放。

### 8.3 故障策略

| 故障 | 策略 | 群内行为 |
|---|---|---|
| 400/422 请求参数错误 | 不自动重试，检查兼容/配置 | 仅有效 @ 下简短失败提示 |
| 401 鉴权失败 | 停用异常提供商调用，通知维护侧 | 不泄露密钥或响应细节 |
| 402 余额不足 | 暂停付费请求及抽取 | 有效 @ 下提示暂不可用，控制命令仍可执行 |
| 429 限流 | 限并发，期限内有限退避；可读取可靠 Retry-After，但不假定必有 | 排队已满时对有效 @ 返回一次固定忙碌提示 |
| 500/503、连接中断 | 最多重试 1 次，总期限不重置；合并 SDK 自动重试 | 超时后结束，不无限等待 |
| 模型空结果/无效候选 | 聊天给固定提示；提取直接放弃 | 不把推理文本充当回答 |
| NapCat/QQ 离线 | 维护侧状态可见，待恢复连接 | 不对已过期消息补发成批回复 |
| 记忆库读取失败 | 如果无法确认授权/退出或删除状态，停止受影响采集/调用/发送 | 不以“不用记忆”绕过未知的上下文权限 |
| 仅抽取失败且权限状态完整 | 放弃该次抽取，保留正常聊天 | 无后台群通知，不声称已保存 |
| 删除请求执行失败 | 保持相关读写/采集关闭，记录待维护错误，不能虚报已删除 | 在有效 @ 下明确未完成；恢复前不重启相关能力 |
| 启动清理失败（S2-08） | 只记清理失败计数与审计，**不**置粘滞降级：过期轮次在读侧本就不会进入请求 | 无群内提示；维护者从 `千鹤 状态` 的"清理失败：N 次"与日志得知，重跑清理命令即可再试 |
| 授权修订变化 | 丢弃在途结果并阻止写历史/写记忆 | 必要时在原有效 @ 下给固定重试提示 |
| 预算耗尽 | 停止新模型任务，抽取优先停用 | 有效 @ 下简短提示；不转投未授权服务 |

错误处理仅向已有有效 @ 交互发送固定回复；后台任务、普通闲聊和未允许群不发故障广播。固定提示不再次调用 LLM。

## 9. Mac 验证与 Linux 部署

### 9.1 Mac 本地验证

- AstrBot 源码项目由 uv 运行，NapCat 独立安装和启动；两者优先回环连接。
- NapCat 官方 Shell 文档当前列出 Mac 安装器，要求 macOS 12.0 及以上；具体 CPU 架构、QQ 客户端版本与安装方式仍需联调，不能只凭系统版本认定兼容。
- 使用专门测试群，不以主账号长期运行作为前提。登录/客户端修改属于实施操作，本轮不执行。
- 如果本机组合不可用，可在独立 Linux 环境运行 NapCat 并通过受控私网验证，但必须单独确认拓扑，不直接公开 OneBot 端口。
- Mac 休眠、关机或网络变化会中断服务，不作为长期在线承诺。

### 9.2 Linux 长期运行

- 推荐首版在单机上以非特权服务用户运行 AstrBot 和独立 NapCat 服务，由系统服务管理器监督；保持与本地相同的受控 AstrBot/插件版本。
- NapCat 的 QQ 客户端、系统依赖与 CPU 兼容组合独立记录。如果后续选择容器化 NapCat，固定镜像版本/摘要，不使用漂移的 latest。
- 本机进程间可使用回环地址；若跨容器或主机，按实际可达地址和私网规则配置，不把容器 localhost 当成其他服务。
- AstrBot 源码/锁文件、运行数据、秘密配置分开管理；应用升级不覆盖数据目录。
- 单机进程退出可以由监督器恢复，但 QQ 账号登录失效可能需要人工处理，不能把自动重启当成自动恢复登录。

### 9.3 网络和管理面

- 反向 WebSocket 由 NapCat 主动连向 AstrBot；默认端口在官方文档中为 6199，路径 `/ws`，属于部署参数而不是强制标准。
- Token 两端一致且不为空。单机优先回环绑定；跨主机采用受控私网或加密通道，并限制来源。
- AstrBot WebUI 官方默认端口为 6185；NapCat 管理面也需限制访问。通过 SSH 隧道或受控管理网络访问，不开放互联网匿名访问。
- 变更初始管理凭据、限制配置文件权限；不要照抄官方开发示例中的宽监听地址为生产安全方案。
- 外出访问仅允许实际需要的 QQ/DeepSeek/依赖源等用途；本设计不提供绕过平台限制的机制。

## 10. uv 与版本管理

### 10.1 分清版本层次

| 层次 | 管理方式 |
|---|---|
| 项目代码 | 后续使用 Git 固定本项目及 AstrBot tag/commit；uv 不替代源码版本控制 |
| uv 工具 | 记录并固定验证过的 uv 版本 |
| Python | uv 安装/选择；记录完整版本，用 `.python-version` 固定解释器请求 |
| Python 包 | `pyproject.toml` 声明、`uv.lock` 锁定、uv 同步 |
| 插件 | 固定插件源码版本；依赖进入与运行环境一致的受控集合 |
| NapCat/QQ | 单独固定兼容版本、下载来源或镜像摘要 |
| 系统 | 记录 Mac/Linux 系统与 CPU；不能只复制 `.venv` 跨平台迁移 |

### 10.2 源码路线

采用官方支持的 AstrBot 源码部署路线，不在外层新建空 Python 项目后宣称它已经锁定 AstrBot 全部依赖。

操作语义如下；当前已执行的环境准备与测试命令见第 14 节，服务启动仍未执行：

| 操作 | 用途与约束 |
|---|---|
| `uv python pin <已验证完整版本>` | 在实际项目位置记录解释器选择；`requires-python` 仍表示兼容范围，两者不同 |
| `uv lock` | 受控依赖变更时解析并更新锁文件，不在日常生产启动中隐式升级 |
| `uv lock --check` | 检查声明与锁一致性 |
| `uv sync --locked` | 按已有有效锁同步，锁需更新则失败；会改变环境，不是只读检查 |
| `uv run --locked main.py` | 对官方源码入口的拟议运行方式；以选定版本实际入口为准，不允许自动改锁 |
| `uv run --no-sync main.py` | 仅在环境已经按锁验证同步后使用；不能证明额外插件依赖已锁定 |

官方源码部署文档要求 Python >=3.12。现已克隆并核对 AstrBot v4.28.1 的实际依赖声明：该提交没有 uv.lock。经用户补充授权，已用 uv 生成并保存项目受控锁 `environment/uv.lock`，详情见第 14 节；上游声明和业务源码保持不变。

若所选版本缺少可复用锁文件，应在受控构建步骤生成并审阅相应锁；不能以未锁定 requirements 文件或只固定 AstrBot 包版本冒充完整复现。

### 10.3 插件依赖治理

- 禁止直接 `pip`、`pip3`、`python -m pip` 安装，包含间接调用这些命令的插件/管理器/修复脚本。
- 主流程统一采用 uv 项目管理，不需要用户运行任何直接 pip 命令。`uv pip` 虽然是 uv 的兼容接口，本方案也不以临时追加包替代锁定。
- 所选 AstrBot 版本的插件安装后端需源码/运行审计；存在 `pip_install_arg` 等配置名不证明它实际会或不会执行 pip。
- 项目插件依赖需纳入所选 AstrBot 部署项目的受控声明/锁集合。选择何种 dependency group 或部署 overlay，以选定上游文件结构为准，不在这轮捏造现成扩展机制。
- 首版只启用必要插件，禁用未经审核的插件商店自动安装/更新及运行时自动修复。
- `uv sync` 默认精确同步，会删除锁外额外包；不能让插件动态安装与锁定互相覆盖。
- `--frozen` 不核对声明是否与锁一致，不能替代 `--locked`；`--no-sync` 也不能掩盖环境漂移。
- Mac 与 Linux 复用同一受控声明/锁定基线，允许平台标记导致不同安装集合；每个平台分别验证，绝不复制虚拟环境。

### 10.4 升级和回退

固定 AstrBot、插件、Python、uv、NapCat/QQ 组合与模型配置基线。受控升级先在测试环境执行同一验收矩阵，再切换生产；避免同批改变所有组件而无法定位问题。

回退以代码、锁文件和兼容配置为主。涉及 SQLite/原生历史格式变更时先评估兼容性；在首版不备份成员数据的约束下，可能需要清空相关数据并重新授权，不能承诺任意版本无损回退。
